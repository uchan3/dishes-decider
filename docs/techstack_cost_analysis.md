## 1. 結論（TL;DR）

| 論点 | 結論 |
|---|---|
| LLM は自前ホスティングすべきか | **No。** ローカル LLM の電気代がクラウド API 料金を上回る |
| Claude API はコスパが悪いか | **個人利用規模では誤解。** Haiku 4.5 なら 1 件あたり約 1.4 円、月 50 件で **約 70 円** |
| では最大のコストは何か | **Apple Developer Program（$99/年 ≒ 15,000 円/年 = 月 1,250 円）** LLM 費用の 10〜20 倍 |
| 本当に無料にする方法 | **PWA + iOS ショートカット**で配信する。Apple 年会費が丸ごと不要になる |
| LLM の推奨 | **Gemini Flash 無料枠を主、Claude Haiku 4.5 を品質フォールバック。** プロバイダ抽象化で切替可能に |
| 到達可能な月額 | **0 円**（PWA 構成）／ **約 1,400 円**（ネイティブ iOS 構成） |

## 2. 前提とする利用量

個人＋パートナーの 2 人世帯での現実的な見積り。

| 項目 | 想定値 | 根拠 |
|---|---|---|
| レシピ取り込み | 20〜50 件/月 | 週 5〜12 件。実際には初期にまとめて登録し、その後は逓減する |
| うち LLM 抽出が必要 | 60〜70% | JSON-LD が取れる Web レシピは LLM をスキップできる |
| 献立生成 | 4〜8 回/月 | 週 1 回 + 再生成。**クライアント側で完結するため LLM 不使用** |
| 買い物リスト生成 | 4〜8 回/月 | 同上。純粋な集約処理で LLM 不使用 |
| DB サイズ | 年間 10 MB 未満 | 手順は要約テキストのみ、画像は保存しない |
| MAU | 2 | — |

**重要**: 献立生成と買い物リストは LLM を使わない。LLM が必要なのは**レシピ取り込みの瞬間だけ**であり、しかも 1 レシピにつき生涯 1 回で済む（結果を DB に保存するため）。これがコスト構造を決定づける。

## 3. LLM コストの実測見積り

1 回の抽出あたり **入力 5,000 トークン / 出力 800 トークン** と仮定する（YouTube 概要欄や整形済み HTML 本文 + プロンプト、出力は構造化 JSON）。

| モデル | 単価 (入力/出力 per MTok) | 1 件あたり | 月 50 件 | 月 200 件 |
|---|---|---|---|---|
| Gemini 2.5 Flash / Flash-Lite（無料枠） | $0 | **0 円** | **0 円** | **0 円** |
| Claude Haiku 4.5 | $1 / $5 | 約 1.4 円 | **約 70 円** | 約 280 円 |
| Claude Sonnet 5（導入価格） | $2 / $10 | 約 2.8 円 | 約 140 円 | 約 560 円 |
| Claude Sonnet 5（9/1 以降） | $3 / $15 | 約 4.2 円 | 約 210 円 | 約 840 円 |
| Claude Opus 4.8 | $5 / $25 | 約 7.0 円 | 約 350 円 | 約 1,400 円 |

> Claude の価格は 2026 年 7 月時点。Sonnet 5 は 8/31 まで $2/$10 の導入価格、9/1 から $3/$15。
> Batch API で 50%、プロンプトキャッシュで入力を最大 90% 削減できるが、本用途では 1 件ずつの即時処理なので適用しづらい。

### 3.1 さらに削るための構造的な工夫

| 手法 | 削減効果 | 実装難度 |
|---|---|---|
| JSON-LD が取れたら LLM をスキップ | 呼び出し回数を 30〜40% 削減 | 低。仕様書 F-01-1 に既に定義済み |
| URL ハッシュで抽出結果をキャッシュ | 同一レシピの再取り込みが 0 円 | 低 |
| HTML から本文のみ抽出してから投入 | 入力トークンを 50〜70% 削減 | 中。Readability 系ライブラリで対応 |
| 抽出とタグ付けを 1 回の呼び出しに統合 | 呼び出し回数を半減 | 低。既にスキーマ統合済み |

HTML の前処理は効果が大きい。生 HTML をそのまま投げると 20,000 トークンを超えることがあり、本文抽出するだけでコストが 1/4 になる。

## 4. ローカル LLM の実現性検証

「API 料金を払わずに済む」ことを期待して検討したが、**結論として金銭的なメリットはない。**

### 4.1 実行場所ごとの評価

| 実行場所 | 実現性 | 判定 |
|---|---|---|
| **スマホ端末上（オンデバイス）** | React Native から llama.cpp / MLC-LLM を叩く構成。3B 級の量子化モデルしか載らず、日本語の崩れたレシピテキストから構造化 JSON を安定生成する精度に届かない。アプリサイズが 2〜4 GB 増える | **却下** |
| **自宅サーバー常時稼働（Mac mini / PC + Ollama）** | 品質は 8〜14B 級で実用圏。ただし後述のコスト逆転が発生 | **非推奨** |
| **自宅サーバー間欠稼働 + ジョブキュー** | 抽出は非同期なのでキュー化は可能。ただしサーバー起動待ちで取り込みが数時間遅延する | **UX 劣化が大きい** |

### 4.2 コストの逆転（これが決定的）

自宅サーバーを常時稼働させる場合の電気代：

```
Mac mini M4 の平均消費電力（アイドル主体 + 時々推論）  約 10 W
10 W × 24 h × 30 日 = 7.2 kWh/月
東京電力の従量単価 約 31 円/kWh
→ 電気代のみで 約 223 円/月
```

**月 50 件の抽出なら Claude Haiku 4.5 が約 70 円。ローカル運用の電気代の方が 3 倍高い。** ハードウェア購入費（10 万円〜）と、Cloudflare Tunnel などで外部から到達可能にする構築・保守の手間は別途かかる。

### 4.3 それでもローカルを選ぶ理由があるとすれば

金銭以外の動機なら成立する。

- **学習目的**: Ollama / 量子化 / GBNF による構造化出力制約などは、実務でも効く知識である
- **プライバシー**: 送信するのは他人が公開したレシピ本文なので、本用途では重要度が低い
- **無料枠のデータ利用ポリシー回避**: Gemini 無料枠はプロンプトが学習に使われうる（後述）

**推奨**: コスト削減のためにローカル LLM を選ぶのはやめる。ただしプロバイダ抽象化（§5）を入れておけば、後から Ollama を差し込んで学習用に遊ぶことはいつでもできる。

## 5. LLM プロバイダの推奨構成

### 5.1 段階戦略

```
[Tier 0] JSON-LD パース          → LLM 不使用。最優先
[Tier 1] Gemini Flash 無料枠      → 通常の抽出。0 円
[Tier 2] Claude Haiku 4.5        → Tier 1 が失敗 / 品質不足時のフォールバック
[Tier 3] 手動入力                 → すべて失敗時
```

### 5.2 Gemini 無料枠の実力と注意点

| 項目 | 内容 |
|---|---|
| 対象モデル | Flash / Flash-Lite 系（Pro は 2026 年 4 月に無料枠から除外） |
| RPD | Flash-Lite で 1,000〜1,500 件/日。Flash で 250〜1,500 件/日（情報源により差あり） |
| RPM | 15〜30 |
| クレジットカード | 不要 |
| 商用利用 | 可（EU/EEA/UK/スイスを除く。**日本は対象内**） |
| 構造化出力 | `responseSchema` によるネイティブ対応あり。JSON 抽出用途に向く |
| **注意点** | **無料枠ではプロンプトと応答が Google のモデル改善に利用されうる** |

想定利用量（月 20〜50 件）は日次上限の 1/30 以下であり、**無料枠で完全にカバーできる**。

データ利用ポリシーについては、送信内容が「公開されているレシピ本文」と「自分の食材メモ」であるため、私的利用の範囲では許容範囲と判断する。気になる場合は Tier 2 の Claude に寄せれば月 100 円未満で済む。

### 5.3 プロバイダ抽象化（設計上の必須事項）

抽出処理は Supabase Edge Function 内でプロバイダを差し替え可能にする。

```typescript
interface ExtractionProvider {
  name: 'gemini' | 'claude' | 'ollama';
  extract(input: ExtractionInput): Promise<RecipeExtractionResult>;
}
```

これを入れておく理由は 3 つ。

1. 無料枠のポリシー変更（2025 年 12 月に Gemini の枠が 50〜80% 削減された前例がある）に対する保険
2. **抽出品質の A/B 比較ができる。** 仕様書で定義した類似度スコアをプロバイダ別に集計すれば、どのモデルが要約タスクに向くか実データで判断できる
3. 学習目的で Ollama を差し込める

### 5.4 品質にはケチらない

抽出品質は仕様書 §F-01 で述べた通り**プロダクトの生命線**である。材料の取りこぼしは買い物リストの破綻に直結する。

1 件 1.4 円のコストを削るために精度の低いモデルを選ぶのは、明確に割に合わない。**Tier 1 で品質が出ないと判断したら、迷わず Tier 2 を常用にすべき。** 月 200 件でも 280 円である。

## 6. 最大のコスト要因：配信形態

**ここが本当の勝負どころ。** LLM 費用の 10〜20 倍の差がつく。

### 6.1 選択肢の比較

| 方式 | 初期費用 | 年額 | 共有シート | 備考 |
|---|---|---|---|---|
| **PWA（Web アプリ）** | 0 円 | **0 円** | iOS ショートカットで代替可 | App Store 審査なし |
| ネイティブ + 無料プロビジョニング | 0 円 | 0 円 | ○ | **7 日ごとに Xcode で再署名が必要**。実用に耐えない |
| ネイティブ + Apple Developer Program | 0 円 | **約 15,000 円** | ○ | TestFlight / App Store 配信が可能 |

<!-- App Store 公開を前提としない限り、年会費は純粋なランニングコストになる -->

### 6.2 PWA の弱点と、その回避策

PWA を選ぶ最大の懸念は「iOS で共有シートに出せない」ことだった。Web Share Target API を Safari が実装していないためである。

**しかし iOS ショートカットで完全に代替できる。**

```
[共有シート] → [ショートカット「レシピを保存」]
                  ↓ 共有された URL を受け取る
                [Web リクエストで Supabase Edge Function に POST]
                  ↓
                [抽出パイプラインが非同期で走る]
                  ↓
                [完了通知（ショートカットの通知 or PWA の Web Push）]
```

ショートカットは「共有シートに表示」を有効にすれば、Instagram / YouTube / Safari の共有メニューに直接並ぶ。ネイティブの Share Extension と体感が変わらない。**しかも実装は 10 分程度で、コードを 1 行も書かずに済む。**

### 6.3 PWA のその他の制約

| 制約 | 影響 | 対策 |
|---|---|---|
| Safari のストレージ退避（7 日間未使用で IndexedDB が消えうる） | 中 | ホーム画面に追加した PWA は対象外。かつ毎日使うアプリなので実害なし。正はサーバー側 DB |
| Web Push | 小 | iOS 16.4+ でホーム画面追加済み PWA は対応 |
| App Store 配信 | — | 個人利用なら不要 |
| カメラ / OCR | 小 | `getUserMedia` + Tesseract.js で対応可 |

### 6.4 推奨

**PWA から始める。** 理由は費用だけではない。

- 年会費 15,000 円を「まだ使い続けるか分からないアプリ」に先払いしなくて済む
- ビルド・審査のサイクルがなく、`git push` で即反映される。個人開発の速度が段違い
- 半年使い続けて手放せなくなったら、その時点で Expo に移植して年会費を払えばよい

ただし Yutaro さんの目的が「iOS アプリ開発の経験を積むこと」なら、話は別。その場合は Expo + Apple Developer Program を最初から選ぶべきで、年会費は学習投資として計上する。

## 7. インフラ各層の無料枠

| レイヤ | サービス | 無料枠 | 本用途での消費見込み | 判定 |
|---|---|---|---|---|
| DB / Auth | Supabase Free | DB 500 MB、MAU 5 万、帯域 5 GB、プロジェクト 2 つ | DB 10 MB 未満、MAU 2 | ◎ 余裕 |
| サーバーレス | Supabase Edge Functions | 50 万呼び出し/月 | 100 回未満/月 | ◎ 余裕 |
| フロント配信 | Cloudflare Pages | 帯域無制限、ビルド 500 回/月 | — | ◎ |
| フロント配信（代替） | Vercel Hobby | 帯域 100 GB/月 | — | ◎ |
| LLM | Gemini Flash 無料枠 | 1,000〜1,500 RPD | 2 件/日 | ◎ 余裕 |
| ネイティブビルド（将来） | EAS Free | iOS 15 ビルド/月 | — | ○ |
| CI | GitHub Actions | 2,000 分/月（プライベートリポジトリ） | — | ○ |

### 7.1 Supabase の唯一の注意点：7 日間無操作でプロジェクトが一時停止する

無料枠のプロジェクトは 7 日間 DB アクセスがないと自動停止し、復帰に 30 秒ほどかかる。

**本用途では実質的に問題にならない。** 献立と買い物リストを毎週使うため、7 日連続で無操作になることは考えにくい。ただし旅行などで空く可能性を考えるなら、GitHub Actions で 3 日おきに軽いクエリを投げる cron を置けば完全に回避できる（無料枠内）。

## 8. 推奨構成

### 案 A: ゼロ円構成（推奨）

```
フロント      Next.js or Vite + React（PWA 化）
              → Cloudflare Pages にデプロイ
ローカル DB   IndexedDB（Dexie.js）※買い物リストのオフライン動作用
バックエンド  Supabase（Postgres + Auth + Edge Functions）Free プラン
LLM           Gemini Flash 無料枠（プロバイダ抽象化の裏）
取り込み導線  iOS ショートカット → Edge Function への POST
埋め込み      YouTube iframe / Instagram ディープリンク

月額: 0 円
```

### 案 B: 品質重視構成

案 A の LLM を **Claude Haiku 4.5** に置き換える。

```
月額: 約 70〜300 円
```

無料枠のデータ利用ポリシーが気になる場合、または Gemini の抽出品質が実測で不足した場合はこちら。

### 案 C: ネイティブ構成（将来 / 学習目的）

```
フロント      Expo (React Native) + expo-share-extension
バックエンド  案 A と同じ
配信          TestFlight（Apple Developer Program 必須）

月額: 約 1,250 円（年会費）+ LLM 費用
```

Saving Calendar と技術スタックを揃えたい、App Store 公開の経験を積みたい、という場合。

## 9. 段階的な移行計画

```
Phase 1（M1〜M3）: 案 A で作り切る
  ├─ 費用 0 円のまま MVP を完成させる
  ├─ 抽出品質・献立生成・買い物リストの有効性を実データで検証
  └─ プロバイダ抽象化を入れておく

Phase 2: 実測データで判断
  ├─ 抽出の類似度スコアと材料取りこぼし率を計測
  ├─ Gemini で足りていれば据え置き
  └─ 不足なら Claude Haiku に切替（案 B）

Phase 3: 継続利用が確定したら
  ├─ 半年使い続けているか？
  ├─ YES → ネイティブ移植を検討（案 C）
  └─ NO  → PWA のまま。年会費を払わずに済んだ
```

**Phase 3 の判断を先送りできることが、この計画の最大の価値。** 15,000 円/年のコミットを、プロダクトの価値が実証されるまで遅らせられる。

## 11. 補足：コスト感覚のまとめ

参考として、月額を身近な支出と並べる。

| 項目 | 月額 |
|---|---|
| 案 A（PWA + Gemini 無料枠） | **0 円** |
| 案 B（PWA + Claude Haiku、月 50 件） | 約 70 円 |
| 案 C（ネイティブ + Claude Haiku） | 約 1,320 円 |
| 自宅サーバーの電気代のみ | 約 223 円 |
| Supabase Pro（不要） | 約 3,900 円 |
| コンビニコーヒー 1 杯 | 約 180 円 |

**案 B の月額は、コンビニコーヒー半分以下。** ここを削るために設計を歪めるのは、時間対効果が明確に悪い。最適化すべきは配信形態（§6）であって LLM ではない。
