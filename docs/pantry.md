# 冷蔵庫（使い切りリスト）仕様 v0.1

家にある食材を献立と買い物に反映し、「同じものを買ってしまう」「奥で腐らせる」を減らす。

## 1. 目的と非目的

**非目的**: 厳密な在庫管理と自動消し込み（Spec §2.2 の非スコープを踏襲）。数量も持たない。

**設計の第一条件**: 在庫が現実とズレても、**献立生成の加点が少しズレるだけ**で、買い物リストも献立も壊れないこと。
この手の機能が死ぬのは「在庫データが現実と合わなくなり、誰も更新しなくなる」ときなので、
ズレることを前提に、ズレても実害が出ない置き方にする。

## 2. データモデル

```
pantry_items
  id            uuid  primary key   ← ingredients.id と同じ値を使う
  user_id       uuid  not null
  added_at      timestamptz not null default now()
```

**主キーに食材 ID をそのまま使う。** 「同じ食材は 1 行」という制約と一致し、
二人が同時に同じ食材をチェックしても **id が一致するので upsert が衝突しない**
（別 id + unique 制約にすると、片方の送信が unique 違反で永久に失敗する）。

数量・メモ・賞味期限は**列ごと作らない**。使われない入力欄を抱えるより、必要になってから足す。

同期は既存の outbox（行単位）に載せる。削除も `delete` として送られる。

## 3. 入り

| きっかけ | 挙動 |
|---|---|
| 買い物リストでチェック | 即、在庫に追加 |
| チェックを外す | 在庫からも外す（**対称にする**。押し間違いを戻せる） |
| 冷蔵庫画面から手動追加 | 食材マスタから選ぶ（表記ゆれを持ち込まない） |

- `ingredient_id` が null の項目（トイレットペーパー等の手動追加）は対象外
- 常備品は買い物リストに出ないので在庫にも入らない。加点の計算でも分母から外すので中立

## 4. 出（4 経路）

| 経路 | 挙動 |
|---|---|
| 「作った」時に提示 | 献立で「作った」を押すと、そのレシピの材料に該当する在庫だけを一覧表示（既定は全チェック）→ ワンタップ確定。閉じても在庫は変わらない |
| 冷蔵庫画面で手動削除 | 一覧から × |
| 古いものの確認 | 追加から一定日数を過ぎたものを「そろそろ？」と薄く表示。**自動削除はしない**。閾値は売場カテゴリで変える（生鮮=野菜/肉/魚/乳卵は 5 日、乾物/冷凍/調味料/その他は 14 日） |
| 買い物リストから戻す | 「家にあるかも」に畳まれた項目をタップ →「実は無い」で在庫から外し、買う側に戻す |

**在庫が増える一方になるのが最大の失敗モード**なので、出の経路を 4 つ用意している。

## 5. 献立生成の加点（控えめ）

core の `scoring.ts` に 1 項目追加する。

```
+ w6 * pantry_score
pantry_score = 在庫にある材料数 / 対象材料数
  対象材料 = ingredient_id があり、常備品でなく、曖昧量（適量・少々）でないもの
  対象が 0 なら 0（無得点。ペナルティにはしない）
```

- **ハードフィルタにはしない**。在庫が空でも生成は今までどおり動き、在庫が偏っても献立が偏りすぎない
- 重みは favorite / recency と同程度。**設定項目は作らない**（増やすほど誰も触らなくなる。効きが弱ければ定数を調整する）

## 6. 買い物リスト

在庫にある材料は「**家にあるかも**」セクションに畳む（常備品の除外ロジックの一般化）。
完全には隠さない — 隠すと「在庫が古いまま買い忘れる」に気づけない。件数は常に見せる。

## 7. 「今作れる」検索

- ライブラリの並べ替えに「在庫で作れる順」（`pantry_score` の降順）
- 各レシピに「あと N 品」（不足している対象材料の数）
- 絞り込み「あと 2 品まで」

計算は献立生成と同じ純粋関数を core で共有する。

## 8. UI

買い物タブの上部に切替を置く。下タブは 5 つのまま。店でも家でも同じ場面で使うので行き来が自然。

```
── 買い物 ──────────────
 [ 買うもの ] [ 冷蔵庫 ]

 ☐ 玉ねぎ       2個
 ☐ 豚こま切れ肉  300g
 ▾ 家にあるかも (3)
```

## 9. 実装の分割

| | 内容 |
|---|---|
| P1 | データモデル・同期、買い物チェック連動、冷蔵庫画面（一覧・手動追加・削除）、「家にあるかも」 ✅ |
| P2 | 献立生成の加点（core）、「今作れる」検索 ✅ |
| P3 | 「作った」時の提示、古いものの確認表示 |

P1 だけでも「重複購入が減る」価値は出る。P3 は運用してから形を調整したいので最後。

## 10. 実装メモ

- 加点の重み `pantry` は 0.8（favorite と同程度）。**レシピ数が枠数に対して少ないと効果は見えない**
  （候補が枯れて緩和が入るため、スコアが選択を左右しない）。手元のサンプル 12 件・16 枠では
  在庫ありレシピの採用率が 30% → 31% と誤差の範囲だった。効きが弱いと感じたら定数を上げる
- 「あと N 品」は突き合わせ対象が 0 件のレシピでは表示しない（材料が未紐付けのレシピを
  「あと 0 品＝今作れる」と誤表示しないため）

## 11. 残るリスク

- 在庫が増える一方になる可能性。P1 リリース後に件数の推移を見て P3 の形を決める
- 二人運用で、同期が届く前に相手が献立を作ると加点がズレる。実害は小さいので許容する
